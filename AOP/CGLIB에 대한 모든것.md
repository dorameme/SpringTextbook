# 프록시 개념 정리 (CGLIB vs JDK 동적 프록시)

Spring AOP에서 사용하는 두 가지 대표적인 프록시 방식인 CGLIB과 JDK 동적 프록시에 대해 정리한다.

<details> 
  <summary><strong>프록시가 필요한 이유</strong></summary>

"왜 굳이 프록시를 써야 할까?" — 이건 스프링 AOP나 DI를 이해하는 핵심 질문 중 하나다.

---

## 프록시가 필요한 이유

프록시는 핵심 로직 외의 기능을 코드에 직접 넣지 않고 따로 처리할 수 있게 해준다.
즉, 관심사의 분리(Separation of Concerns) 를 실현하기 위해 사용한다.

### 1. 공통 기능을 재사용하고 분리하기 위해

예를 들어, 모든 서비스 메서드에 대해 다음을 수행하고 싶다고 가정하자:

 실행 전 로그 출력
 실행 시간 측정
 예외 발생 시 별도 처리

이걸 각 서비스 메서드에 직접 코드로 넣으면 다음과 같은 문제가 생긴다:

 중복 코드가 많아진다
 코드가 지저분해진다
 유지보수가 어렵다

→ 프록시를 사용하면, 모든 메서드 실행 전에 공통된 로직을 자동으로 끼워 넣을 수 있다.
원래 로직은 손대지 않고, 공통 로직만 프록시 객체에 따로 정의하면 된다.

---

### 2. 원본 코드를 건드리지 않고 기능을 추가하기 위해

예를 들어, 외부 라이브러리나 다른 팀이 만든 코드는 내가 마음대로 수정할 수 없다.
하지만 로깅, 보안 체크, 트랜잭션 처리 등을 추가하고 싶을 수 있다.

→ 프록시를 사용하면 원본 코드에는 전혀 손대지 않고, 기능을 “감싸서” 추가할 수 있다.

---

### 3. AOP (Aspect Oriented Programming) 구현을 위해

AOP의 핵심은 \\“코드 흐름에 끼어들어 공통 처리를 하는 것”\\이다.
예: 메서드 실행 전후로 로그 출력, 권한 검사, 트랜잭션 관리 등

이걸 실현하려면 결국 중간에 끼어들 수 있어야 하는데, 이때 필요한 것이 바로 프록시이다.

 JDK 프록시는 인터페이스 기반으로
 CGLIB은 클래스 상속 기반으로

→ 원본 로직의 전후로 우리가 원하는 로직을 삽입할 수 있다.

---

### 4. DI(의존성 주입)과 AOP를 결합하기 위해

스프링 컨테이너는 AOP 적용이 필요한 객체를 빈으로 등록할 때,
프록시 객체를 대신 주입한다.
개발자는 그냥 `UserService`를 사용하는 것처럼 보이지만, 실제로는 `UserServiceProxy`가 동작하는 구조이다.

이 덕분에 개발자는 로직에만 집중하고, 부가 기능은 AOP와 프록시가 알아서 처리해준다.

---

## 정리

| 이유        | 설명                               |
| --------- | -------------------------------- |
| 관심사 분리    | 핵심 로직과 공통 기능(로깅, 트랜잭션 등)을 분리     |
| 유지보수성     | 공통 로직을 한 곳에서 관리 가능               |
| 코드 일관성    | 중복 없이 일괄 처리 가능                   |
| 외부 코드 보완  | 외부 라이브러리나 수정 불가 코드에 기능 추가 가능     |
| AOP 구현 기반 | 전/후 처리 기능을 자연스럽게 끼워 넣을 수 있음      |
| 스프링 DI 연계 | 빈 등록 시 프록시 객체를 대신 주입하여 AOP 자동 적용 |

---

궁극적으로 프록시는 깨끗한 코드, 높은 재사용성, 강력한 확장성을 가능하게 해준다.
AOP, DI, 트랜잭션, 보안 등 스프링의 많은 기능들이 프록시 기반 위에 구축되어 있다는 점에서
프록시는 스프링의 핵심 메커니즘 중 하나라고 할 수 있다.

</details>



<details>
<summary><strong>CGLIB란?</strong></summary>

CGLIB(Code Generation Library)은 바이트코드를 조작하여 런타임에 기존 클래스의 자식 클래스를 동적으로 생성하는 라이브러리이다. 생성된 자식 클래스는 부모 클래스의 메서드를 오버라이딩하여 AOP 같은 부가기능을 삽입할 수 있다.

인터페이스가 없는 클래스에도 프록시를 적용할 수 있는 장점이 있으며, 스프링 프레임워크에서는 AOP 대상이 인터페이스를 구현하지 않은 경우 자동으로 CGLIB이 사용된다.

</details>



<details>
<summary><strong>CGLIB의 동작 방식 (쉬운 설명)</strong></summary>

CGLIB은 기존 클래스를 복제한 하위 클래스를 만들고, 그 안에 메서드를 오버라이딩하여 부가기능을 삽입하는 방식이다.

예를 들어, `UserService`라는 클래스가 있을 때, 이 클래스의 자식 클래스를 동적으로 생성하여 `serve()` 메서드 실행 전후에 자동으로 로깅, 트랜잭션 처리 등을 끼워 넣는다. 원본 클래스는 손대지 않는다.

</details>



<details>
<summary><strong>CGLIB 비유</strong></summary>

요리사 비유  
요리 전 손 씻기, 요리 후 설거지를 자동으로 추가하고 싶을 때, 기존 요리사를 건드리지 않고 복제 요리사를 만들어 그 기능을 추가한 것과 같다.

</details>

<details>
<summary><strong>CGLIB이 final 클래스나 final 메서드에서 동작하지 않는 이유</strong></summary>

CGLIB은 상속을 통해 자식 클래스를 만들고, 메서드를 오버라이딩하여 부가기능을 삽입한다.  
그러나 Java에서 `final` 클래스는 상속이 불가능하고, `final` 메서드는 오버라이딩이 불가능하다.  
따라서 CGLIB이 프록시를 생성하거나 기능을 끼워 넣는 것이 불가능하다.

</details>



<details>
<summary><strong>CGLIB 사용 시 실무에서 주의할 점</strong></summary>

- AOP 대상 클래스에 `final` 키워드 사용 금지
- 인터페이스가 없으면 CGLIB이 자동 선택됨
- 초기 로딩 성능이 JDK 프록시보다 느릴 수 있음
- 프록시 객체는 원본 객체가 아닌 CGLIB 하위 클래스임에 주의
- `@Configuration` 클래스에서는 `final` 메서드를 선언하지 않도록 주의 (싱글톤 깨짐 가능성 있음)

</details>



<details>
<summary><strong>JDK 동적 프록시란?</strong></summary>

JDK 동적 프록시는 Java의 기본 기능으로, 인터페이스 기반으로 동작한다.  
인터페이스를 구현한 클래스에 대해, 런타임에 대리 객체(프록시 객체)를 생성하여 메서드 실행 전후에 부가기능을 삽입할 수 있다.  
스프링에서는 인터페이스가 존재하는 경우 기본적으로 JDK 동적 프록시가 사용된다.

</details>



<details>
<summary><strong>JDK 동적 프록시 동작 방식 (쉬운 설명)</strong></summary>

인터페이스만 있으면, 해당 인터페이스를 구현한 것처럼 동작하는 대리 객체를 만들어, 호출되는 메서드마다 자동으로 원하는 기능을 끼워 넣는다. 실제 로직은 구현 클래스에게 위임한다.

</details>



<details>
<summary><strong>JDK 동적 프록시 비유</strong></summary>

콜센터 비유  
프록시가 고객센터를 대신 받아 응답한다. 전화를 받자마자 "녹음이 시작됩니다"라는 멘트를 먼저 출력하고, 실제 고객센터에 연결해주는 식이다.

</details>



<details>
<summary><strong>CGLIB vs JDK 동적 프록시 비교</strong></summary>

| 항목                     | JDK 동적 프록시                         | CGLIB 프록시                              |
|--------------------------|-----------------------------------------|--------------------------------------------|
| 프록시 대상              | 인터페이스                              | 구체 클래스                                |
| 작동 방식                | 인터페이스를 구현한 가짜 객체 생성      | 자식 클래스를 만들어 메서드 오버라이딩     |
| 인터페이스 필요 여부     | 필요                                     | 불필요                                     |
| final 클래스/메서드 지원 | 가능 (인터페이스 기반이므로 영향 없음)  | 불가능 (오버라이딩 불가)                  |
| 성능                     | 가볍고 빠름                             | 초기 성능은 낮지만 캐시로 개선 가능        |
| 스프링 기본 전략         | 인터페이스 존재 시 기본 사용             | 인터페이스가 없을 경우 자동 사용됨        |

</details>



<details>
<summary><strong>스프링에서 프록시 방식 결정 기준</strong></summary>

- 인터페이스가 있을 경우: JDK 동적 프록시 사용
- 인터페이스가 없을 경우: CGLIB 사용
- 단, 명시적으로 `@EnableAspectJAutoProxy(proxyTargetClass = true)` 설정 시 CGLIB 강제 사용 가능

</details>
